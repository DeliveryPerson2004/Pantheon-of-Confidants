# 方向与取舍

本文记录项目背后的判断，而不是功能清单。已经落地的能力以 [后端架构说明](README.md) 和代码为准；A2A 已用于客户端到 Gexep 的公开边界，也用于四个 Agent 的内部发现与消息委派。MCP、复杂并行调度、审核 Agent 与 GraphRAG 等仍是后续方向，不应混为一谈。

## 直接调用模型 API，保留 model provider 的表达能力

本项目不是只消费一段文本的聊天客户端，而是由模型输出项驱动的 Agent 运行时。DeepSeek `/responses` 返回的 `message`、`reasoning`、`function_call` 和 `web_search_call` 具有不同语义：有些需要记录，有些需要在本地执行并回填，有些则由模型服务自行完成。若过早套用通用 SDK 或统一中间层，这些差异往往会被压缩成“文本 + 工具调用”的最小公约数。

因此，项目选择使用原生 `fetch` 调用 API，并依据官方协议编写 TypeScript 类型。代价是 `responses.ts`、`ModelClient` 和 `BaseAgent` 会与 DeepSeek 协议共同变化；收益则是请求字段、输出项和循环终止条件都清晰可见，不需要依赖 `any` 或隐藏的适配逻辑。

这里并不追求“无条件切换模型”。更换 provider 时，协议差异不会因为抽象而消失，只会转移到适配层。把耦合限制在 `BaseAgent ⇄ ModelClient ⇄ responses.ts` 这条窄链路上，比提前维护一个尚无真实需求的通用模型接口更符合当前项目规模。

## Workflow 与 Agentic 是决策权分配的连续光谱

一种常见观点将 Workflow 和 Agentic 视为光谱的两端：区别不在于系统是否调用了大模型，而在于多少决策权被交给了大模型。执行步骤、分支条件、工具选择和终止规则越多地由代码预先规定，系统就越接近 Workflow；模型越能根据目标自行拆解任务、选择工具、调整路径并判断何时结束，系统就越接近 Agentic。

这不是非此即彼的架构分类，而是一组可以分别调节的控制权。同一套系统可以用确定性的 Workflow 固定权限、审核和外部副作用等边界，同时在边界内让 Agent 处理难以预先枚举的判断。因而，追求 Agentic 不等于把所有控制都交给模型；更重要的是识别哪些决策需要模型的适应性，哪些决策应继续由代码、策略或人来保证确定性。

## 数据只有两张表时，不引入 ORM

当前持久化模型只有 `agent` 和 `message` 两张表，主要操作是按 Agent 查询 ID、恢复已激活的消息以及写入本轮上下文。对于这种稳定且简单的数据形态，ORM 带来的 schema DSL、生成步骤、迁移工具和适配层多于它节省的查询代码。

项目已经从 Prisma 迁移到 `better-sqlite3`：表结构由 `CREATE TABLE IF NOT EXISTS` 初始化，查询集中为 prepared statements，数据库仍是一个可直接查看和备份的本地文件。这不是对 ORM 的普遍否定，而是让抽象成本与实际数据复杂度相匹配。

## MCP 的价值在边界，而不在工具的数量

MCP 适合解决“能力由外部服务提供”时的发现与调用标准化：例如地图、企业数据源或未来的共享记忆服务。此时 Agent 与工具跨进程、跨机器甚至跨组织，统一的 list/call 语义和参数 schema 能减少重复集成。

如果能力与 Agent 位于同一进程和同一信任域，例如读取本地 Skill 或调用项目内函数，再包装一层 MCP server 只会增加部署与调试成本。判断是否使用 MCP 的关键不是“它是不是工具”，而是“实现归谁所有、是否真的跨越边界”。

当前工具都以本地 function tool 直接集成；计划中的 MCP client 将面向第三方服务，而不是把已有的本地函数重新协议化。

## Sandbox 承担执行边界，最小权限决定工具归属

逐条批准工具调用只能表达一次授权，不能代替可靠的执行边界。对于需要运行命令的 Agent，更稳妥的做法是先把破坏范围限制在可丢弃的 Sandbox 中，再按角色决定哪些工具根本不应出现。人工确认仍适用于发送邮件、删除数据等具有外部影响或不可逆的动作，但不应成为隔离机制本身。

Jezeh 已经采用 E2B Sandbox：命令在网络隔离的远端环境中执行，默认工作目录为 `/memos`，宿主机只暴露一个受限的 Markdown 下载通道。这使“处理备忘录”和“写入宿主机”成为两个边界明确的动作。

长期来看，工具也应按职责拆分。执行 Agent 可以修改沙箱中的工作副本，审核 Agent 则负责检查差异并决定是否形成 Git checkpoint。这样执行权与验收权彼此独立，不需要先创建一个全能 Agent，再依赖频繁弹窗补救权限过宽的问题。

## 上下文隔离应来自路由，而不是用户管理会话

不同角色天然拥有不同的职责、工具、数据和历史。用户不应为了避免上下文污染而反复判断“是否需要新开会话”，就像现实中人会直接寻找合适的专业者，而不是先设计一套会话分区。

第一步已经落地：Gexep 是唯一公开入口，终端 UI 不再实例化或切换后端 Agent，而是通过官方 A2A Client 读取 Agent Card 并以 JSON-RPC/SSE 提交任务。这样 API 暴露范围与用户入口保持一致，也使前端可以独立部署、替换或连接远端 Gexep。

内部发现与通信也已经落地：Gexep、Jezeh、Lexey 和 Zebeh 共享标准 Agent Card 目录，每个 Agent 都能查询其他节点的职责和 Skill，并通过官方 Client 调用其仅回环可达的 A2A 服务。因此它们不再是彼此不可见、不可通信的孤岛。

基础自动委派现已实现：Gexep 可以先发现目标，再通过 `delegate_task` 发送最小充分上下文，等待下游 Task 并验收结果。下一步是多目标并行调度、可恢复的长期 Task、需要补充输入时的交互状态，以及更细的授权策略。

## A2A 不会消除网络边界，Agent 集群正在向云端收敛

A2A 统一的是 Agent 之间的发现、委派和结果交换，并不会自动创造网络可达性。部署在公网的 Agent 无法直接调用 NAT 或防火墙后的局域网 Agent；若为每个本地 Agent 暴露公网入口，又需要额外承担身份认证、证书、端口、隧道和攻击面的治理成本。因此，“云端协调者直接调用任意本地 Agent”并不是一种天然稳固的拓扑。

OpenAI 近期的 Agent API 则呈现出另一条清晰路径：Agent 被定义为项目内可复用的托管资源，运行由带执行环境的 Session 承载，并原生提供多 Agent 协调配置。这意味着 Agent 正从各处自行托管的 HTTP 端点，逐步变成云端控制面统一调度的运行单元；状态、算力、权限和协作关系也更适合在同一集群内管理。

因此，当前形成两层边界：北向只发布 Gexep Agent Card；南向则在 `127.0.0.1` 上为专属 Agent 提供路径作用域的 A2A Card 和消息端点。更合理的长期形态可能是让 Gexep 与专属 Agent 运行在彼此可达的云端集群中，在受信网络内延续这组南向接口；局域网能力则通过主动向外连接的受控网关或连接器接入。必须留在本地的 Agent 也应默认由内向外建立连接，而不是要求公网协调者穿透局域网。

## A2A 任务状态与模型上下文是两类状态

A2A Task 用于协议层的任务跟踪、流式状态和 Artifact 交付，模型上下文则由 `BaseAgent` 与 SQLite 维护。二者不能简单合并：协议调用方可能只需要查询某个任务，而模型需要跨多轮保持对话语境；反过来，模型历史也不应通过任务查询无边界地对外泄露。

当前 A2A Task 保存在进程内，Gexep 的模型历史继续持久化。前端使用服务端生成的 `contextId` 延续会话，但每轮创建新的 Task。由于 `BaseAgent` 持有可变输入数组，服务端会串行执行 Gexep 请求，避免并发任务交叉写入上下文。未来要支持水平扩展、可靠恢复和真正的取消，需要把 Task Store 持久化，并将 AbortSignal 贯穿模型与工具调用链。

## 长上下文不是长期记忆

上下文窗口适合保存正在进行的任务状态，即使其中包含同一 Agent 职责范围内的多个话题，也仍属于短期工作记忆。窗口不断增长后，简单地保留全部原始消息既昂贵，也不能自动形成稳定、可检索的知识。

暂定的长期记忆方向是 GraphRAG：从交互中抽取实体、关系和结论，存入带图能力的 PostgreSQL；查询与写入封装为 MCP server，各 Agent 通过统一客户端访问同一张全局知识图。记忆描述的是用户及其长期事实，不应被割裂成互不相通的 Agent 私有副本。

这一方案仍需继续回答写入时机、事实冲突、遗忘策略、权限隔离和可追溯性等问题。在这些边界明确之前，当前 SQLite 消息历史只承担上下文恢复，不被包装成“长期记忆”。
